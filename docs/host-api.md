# Host backend API contract

The Python backend binds `127.0.0.1:18780`. It runs on the host; Android Docker is only the login/credential bootstrap. The web UI polls `GET /api/status?since=<event_cursor>` every two seconds (ten seconds while the tab is hidden). A client that sends back `settings_revision` (`&settings_revision=<value>`) gets the poll without `setting_details` and `setting_choices`, about 90% of a full status, until a settings refresh changes the revision. There is no SSE endpoint.

## Access and lifecycle

Open `GET /` first. The backend issues the process-local `qn_ui` HttpOnly/SameSite=Strict cookie and embeds a CSRF value in the HTML. Each page load gets its own CSP script nonce (distinct from the CSRF value); every other response carries `script-src 'none'`. Other routes require that cookie; POST requests also require `X-CSRF-Token`. Host and Origin checks allow the configured loopback host/port. Cross-site subresources are rejected; top-level navigation to the landing page is allowed. Request bodies are limited to 64 KiB. Private vendor tokens never go to the browser.

Connection startup owns the native-session lock, renews when needed, registers WSS, correlates replies, consumes pushes, heartbeats and reconnects. Backend restart invalidates UI cookies and organization option handles. Reopen the page after restarting. MCP authorization and its lock are separate from the native session.

## Routes

**Server-side cache.** Cloud reads of notes, summaries, tags, sharing, favorites, quotas and memos are kept in `.private/cache/` (0700 directory, 0600 files) for 24 hours, and option lists for 7 days (`CACHED_ACTIONS` in `web_backend.py`). A response served from the cache carries `X-Cached-At` (Unix seconds of the cloud read). Any POST body may add `"refresh": true` to read from the cloud. Writes drop the entries they affect (`WRITE_DROPS`, plus the note's own tag), also when the write fails or its outcome is unknown. A pending journal for a feature disables caching for that feature's read. `status.cache` gives the entry count and the oldest entry time.

All POST bodies are JSON objects; any other body is refused. `persistent_override` is accepted only as the boolean `true`, not a truthy string. A rejected validation generally returns HTTP 409, an unknown route 404 and an unexpected failure 502.

Error bodies are `{"error", "code", "message"}`. For refusals raised through `public_errors.py` (`refused`, `not_ready`, `unavailable`, `busy`, `outcome_unknown`, `cloud_rejected`) the message is the locally authored reason and is shown in the UI. Every other exception keeps the generic message, so vendor responses, identifiers and URLs never reach the browser. `test_public_errors.py` enforces that public messages are string literals.

## Setting descriptions

Each `GET /api/status` → `setting_details[]` row includes `description`, `value_format` and `meaning_evidence` (`source`, `inferred`, `unknown`). The first two are fixed local English text; UI catalogs translate them. They contain no raw account values. The existing `note`, `evidence`, `scope`, editability, choices and restoration guards remain separate. An unknown key gets explicit unknown semantics and no editor. These fields add no vendor request or mutation. Full description table.

## Settings and mutation semantics

The current catalog reports 22 effective fields and exposes 10: six individual fields, the three generation fields and task-completion alert method. `qwen_work_org_id` is an optional additional setting managed through validated options, and is not currently one of the 22 reported keys. It is distinct from binding metadata `device_org_id`, which remains non-editable.

The generation group contains `auto_generate_minutes`, `auto_generate_minutes_duration` and `auto_generate_minutes_duration_limit`. Source-supported choices and restoration rules are in settings editability. The notification group is described in notification settings.

A device-scoped write over an inherited or absent value creates a persistent override. The client has no verified delete-override API, so it requires explicit confirmation and does not claim to restore inheritance. Existing device overrides can be restored from protected journals. Journals are written before sending, survive timeout/restart and are not cleared on ambiguous or mismatched results. A timeout does not cause automatic mutation retry. Batch acceptance is not assumed atomic; readback checks every written field.

Readiness is a statement by the owner, not a sensor-derived idle proof. A cloud acknowledgement/readback is not proof of a speaker, storage, location, language or summary effect. Device events are separate from ASR text events.

## Private and public state

Native tokens, signing configuration, account/device/organization identifiers, raw responses and restoration values remain in protected backend state. Organization selection uses instance-bound HMAC handles; callers cannot submit a raw organization ID through the notification endpoint. The effective setting catalog redacts internal identity fields. No bind/unbind/reset/firmware, raw arbitrary RPC or arbitrary setting endpoint is exposed.

## Recording ownership correction

A known cloud task without ended state and a positive end timestamp now vetoes ordinary Record and RTC start. The RTC controller checks again after reservation. Absence of a known task remains unknown and does not replace physical readiness. The shared RTC lifecycle withholds automatic Stop after a failed/lost start or invalid/unreceived create receipt unless ownership was established; the unresolved journal remains pending and blocks another run. No generic recovery or forced journal-clear endpoint is added.


## Experimental realtime lifecycle

Status includes `rtc`: active/stopping/pending flags, optional media availability and count-only last result. RTC uses the existing native connection without a second refresh owner. Conflicting controls are rejected while ownership is reserved or unresolved. Pending cleanup blocks new controls across restart. See controller checks and deployment boundary. These routes are deployed in the enabled host service. Read-only refresh and unarmed-start rejection are verified; a new end-to-end RTC hardware test was not performed during deployment.

## Cloud recording task

`status.record_task` contains `available`, `source` (`push` or `query`), host `observed_at`, `read_in_progress`, raw cloud status/detail codes, nullable `real_time_asr`, cloud start/update/end timestamps and `physical_state_verified:false`. Only a validated `dtiot.dinger`/770000 recording-task event establishes the private query context. Account, device, task and recording identifiers are retained only in backend memory/private captures. Missing ASR is unknown, never coerced to false. Older task/update pairs cannot replace newer ones; an in-flight query cannot overwrite a subsequent push. An empty snapshot after restart means no matching event has arrived in that host session.

Dev tools displays source and freshness and offers an explicit refresh. It does not poll the vendor for task state. This is the **last observed cloud task**, which may already be finished; it is never presented as a physical idle/recording sensor. Implementation and replay evidence.

## Transcript sources

Live transcript rows include a fixed `source` value (`dtiot.dinger` or `doc.transcribe`) and an opaque per-process stream label. The backend accepts only the source-defined 770001/Dinger and 86000/Flash pairs, validates transcript payloads, and isolates ordering/finalization by source. Document notifications 86001–86003 never become live text. Diagnostics and replay expose separate numeric `dinger_transcript_candidates` and `conference_transcript_candidates` counters. Source and test evidence.

## Passive live-session diagnostics

`GET /api/status` includes `live_diagnostics`, with counts and a generated capture ID only. Raw received pushes and a summary stay in protected backend storage. Captures stop after their deadline even without browser polling, or at size/row limits. Disk errors stop diagnostics without interrupting transcript processing. The offline `capture_report.py` emits aggregate replay counts only. No physical function is enabled by starting capture. Storage limits, evidence and coordinated test procedure.

## Write results and readback

Mutation results keep `cloud_acknowledged`, `physical_result:"unverified"` and `automatic_retry:false`. If the post-write readback fails, the result still reports the acknowledgement with `cloud_readback_matches:null` and `readback_failed:true`; journals stay in place. A command that gets no reply raises `outcome_unknown` (never retried); a non-200 reply raises `cloud_rejected`. `record_state.phase` is one of `idle`, `pending`, `acknowledged`, `unknown`, `rejected`, `confirmed-stopped` or `open-after-restart`.

## Recording and assistant controls

The shared rail contains Record/Pause/Resume/Stop and an AI Assistant shortcut on every tab. The assistant has a dedicated tab; `#ai_assistant` maps to it. Memo text, loaded saved-note paragraphs and final original live rows can be added to its editable draft. Provisional rows and translations are excluded from live drafting. Existing draft text is preserved; a combined draft over 32,000 characters is refused without truncation. Drafting makes no provider call, is not stored in browser local storage and does not enable automatic forwarding.

## Favorite state and recovery

The host accepts a note UUID only after `list_my_minutes` supplied it through the locked, read-only MCP adapter. Context is bounded to 200 notes and 15 minutes. Each write reads native `minutesDetailV2` first and compares the exact UUID and boolean `collected` with the displayed expected value. A stale value causes a refusal, and an already-correct value causes no write. Native `collectMinutes` uses type 1/2, followed by a fresh detail read.

`note-favorite.json` privately retains the note ID, original/desired values, pending state, acknowledgement and final readback. Failed, cancelled or uncertain writes are not retried. `status.note_favorite_pending` and the health blocker `note-favorite-uncertain` retain uncertainty across restart. Refresh favorite on the affected note performs only a native read and resolves that journal. A different note's read cannot clear it. No note content is edited. Device readiness is reserved for physical actions; this account-metadata write requires an explicit Favorite click and does not arm recording controls.

## Transcript replacement recovery

`status.note_replace_pending` and health blocker `note-replace-uncertain` retain ambiguous or partial outcomes across restart. The protected journal preserves the full native original and requested state. Preview never repeats a write; it clears pending only when the complete note matches the original or requested semantic content. Server-generated word IDs are excluded from semantic comparison, while text/timing/speaker data remain exact. Localized generic speaker labels may therefore cause conservative conflicts. A partial batch or unrelated third state stays pending for manual review. The UI invalidates previews when input changes and clears stale loaded transcript content after a verified save.

## Tag assignment recovery

`status.note_tags_pending` and the health blocker `note-tags-uncertain` preserve an uncertain save across restart. The protected `note-tags.json` stores original/requested membership sets. For assignment, a read of the same note reconciles only either exact set; another note or a third state cannot clear it. For creation, reconciliation requires the acknowledged new tag ID and exact metadata; a lost/invalid receipt never clears on a name match. `status.note_tag_creation` gates the creation UI against older backends. Tag options are session- and note-bound handles; raw tag IDs stay backend-side. Preservation and concurrency.
